## 本轮授权和费用边界

我授权一次隔离实验，使用已有的官方 DeepSeek 配置与凭据，总费用上限 **US$1**，只允许 **1 个 Incident、1 个 Session、1 次 Attempt**。该次正常多轮调查最多 **7 次真实模型请求、13 次工具执行**，工具额度包含自动版本探针。每次模型输出最多 **8192 tokens，包含 reasoning tokens**；每次总输入最多 **65536 tokens，包含指令、工具 schema、历史及协议开销**。单次 SDK 超时最多 60 秒，付费调查墙钟时间最多 15 分钟。

这些是全部同时生效的上限，不是必须消耗的额度。只读工具和费用限制由 Python 确定性守卫执行，不得只写在业务 Prompt 中。不得提高全局 7/13 预算、改变修复权限、切换供应商或模型来规避限制。

- 首次付费前核实模型、官方计费规则、Responses API 参数、当前 SDK 版本和 tokenizer/可验证的 token 上界。按较高时段、全部输入未命中缓存计算最坏费用；每次请求先预留本次最坏费用，再决定是否允许发送。不要把字符估算冒充可靠 token 上界。
- `max_output_tokens=8192` 必须实际进入 HTTP 请求，且确认服务端将推理与可见输出一起计入限制。当前生产 ModelClient 未直接传此参数，隔离入口需要显式处理。无法验证输入/输出/计费上界时，停止付费部分并报告，不能仅靠调用后查 usage 控费。仅请求次数上限不能被描述为美元硬上限。
- SDK、HTTP 和 Runtime 自动重试均为 0。允许同一次成功调查中因真实工具结果发出下一轮请求；HTTP 错误、超时、连接断开、协议解析失败、余额或认证错误出现后停止，不自动重试、续跑、reopen 或新建 Session。已经发出的不确定请求也计入已消耗次数和保留费用。
- 授权绑定本次完整源码 SHA 和唯一实验 ID，首次发送前持久化不可重复消费的实验账本。不能通过换目录或重启进程重新消费授权。失败后的修复和离线检查可以继续，下一次付费实验需要新的用户授权，剩余额度不代表重跑许可。
- 禁止额外收费的连通性探测、模型对照、原生网页搜索、文件解析或其他服务；只使用项目已注册的只读调查工具。不要充值、购买服务或改账户额度。
- 从已有可信本地配置读取凭据，只报告是否存在，不打印值，不写入源码、提交、截图或报告。缺失时明确指出本地配置入口并停在付费前，不要求把密钥贴到聊天。付费原始请求/响应存放在 Git 外受保护的本地目录，报告仅引用脱敏副本与哈希。

## 真实启动、故障与调查

1. 使用独立 `incident-stage1-live-*` Compose 项目、独立卷和数据库；先核实空闲回环端口和子网，不改宿主机 MySQL、原有订单库或其他 Docker 项目。平台 MySQL 与订单 PostgreSQL 是两个不同角色。只启动一份调查执行器。
2. 在模型尚不可发送请求时先启动并验证 MySQL、Alembic、API、前端、订单服务、PostgreSQL、Exporter、Prometheus、Loki、Alloy。核实 MySQL 实际版本、迁移头、三个 Store 的就绪状态、Prometheus target、Loki 实际日志和健康订单。不要先启动无约束的付费 monitor 再补限制。
3. 构建隔离实时入口时，可复用 `IncidentMonitor.process_alerts_once()`、现有 Manager/Worker、`RuntimeLimits` 及正常模型/工具链，或为正常入口注入受控真实客户端。所有模型响应必须来自实际官方接口；不要为获得通过另写一套简化调查逻辑。冻结入口、账本、参数和源码哈希后再允许付费。
4. 核对本轮容器标签、发布端口、订单完整 SHA、健康基线及资源归属，只在本轮订单容器开启 `SIMULATE_CODE_REGRESSION`，按既有规则产生有界 `/order` 流量。故障控制信息与期望答案只存验收侧，不作为标准答案注入业务模型。
5. 等待真实 Prometheus firing alert，经现有告警处理建立唯一调查，再由受控真实 Worker 消费。让模型根据实际工具结果选择调查方向。保存每轮 request/response、HTTP/Provider 状态、call_id、参数、工具输出、usage、Checkpoint、Session 状态和计费账本；额外的人工 HTTP 探测与 Agent 工具调用分开记录。
6. 浏览器验证真实 Incident 的服务/状态筛选、同窗 5xx/P95/CPU/RSS、Loki 日志、调查结论和证据。无数据或错误要如实展示，不能补零、插入固定曲线或只检查 HTTP 200。原始数据与页面显示需要相互核对。
7. 分别判断“接口/协议可用”“运行时预算与持久化正确”“证据引用有效”“根因结论得到支持”。COMPLETED 不等于根因正确，证据不足应保留待核实。模型没有取得某项证据，不得把验收侧已知事实算作它的推理成果。

## 恢复和数据回读

- 所有退出路径使用 finally 关闭本轮故障开关。调查结束或任意异常后，先封闭模型发送通道并停止本轮付费执行器，再进行不调用模型的告警/恢复观测，防止解除故障时自动发起第二次付费调查。
- 只对本轮隔离目标恢复；核实 `/order` 的有效订单响应、故障标志和既有独立业务恢复状态。`/health`、告警解除、调查完成、测试控制器复位均不能单独声称“Agent 已修复业务”。若恢复证据不足，保留 unknown/insufficient。
- 停止本轮 API/执行器后重启本轮 MySQL，再启动只读查询入口，核对 Incident、Session、预算、Checkpoint、事件和工具输出。数据库重启后不重启付费调查。
- 本轮不自动批准或执行 Remediation，不把测试身份操作称为真人审批。必要时只生成待审批提案及真实人工入口。已有 38 项历史审计警告仍按原始事实保留，不为验收清零。
- 保存证据和报告后关闭本轮进程、清除临时凭据。仅可删除核实属于本轮且已归档所需证据的临时容器/网络/卷，保留原有资源与历史数据。构建镜像和非敏感证据可保留。无法恢复或无法确认归属时停止危险操作并报告。
