# P5.3b.1 只读分析与回归验证

## 结论

已确认存在可避免的重复分析上下文累积。`provider_verified=true`、
`valid_chain=true` 且所有成功观测持续属于当前有效证据时，
`Worker._context()` 每轮追加 Runtime 分析输入；`_run()` 成功接收模型响应后，
把包含这些输入的 history 再次保存。因此同一份派生分析会被反复传入并持久化。

本次单指标缓存场景，第 2–7 轮分别有 1–6 份相同分析；第 7 轮有 5 份多余副本。
第 7 轮 input 从关闭分析时的 6,118 字节增至
20,578 字节，增量 14,460 字节。
没有发现该追加分支改写真实 function_call/function_call_output，或增加模型、工具、
缓存预算消耗。开启和关闭分析均为 7 次模型请求、2 次工具执行、5 次缓存命中。

小载荷 7 轮没有触及 4 MiB Checkpoint 上限。另一个明确标记的合成临界前史实验
确认：重复分析可以使原本能落盘的 Checkpoint 超限，并且失败事务保留旧 Checkpoint。
真实模型的上下文容量、原生 token 用量、费用和第三方兼容性没有验证。
本轮没有实施业务修复。

## 最小复现与原因

最小可观察前缀只需 3 轮：

1. Mock 版本探测成功，固定实例 SHA；固定时钟使证据不超过原 15 秒 TTL。
2. 第 1 轮模型请求 `query_metrics(order-service, http_request_rate)`，
   返回当前时刻的 `0.0`；Worker 保存真实调用、观测和输出。
3. 第 2 轮走完整链，追加第 1 份 Runtime 分析；模型再次请求同一指标，命中缓存。
4. 第 3 轮保留第 2 轮已保存的分析，再追加相同分析，输入内共 2 份。
   两份 `metric_analysis` 的序列化 SHA-256 相同，来源 observation_id 相同。

本次 7 轮运行使用的同一 Fixture 观测 ID 为 `obs-614b779c4b414aebaee5ac9ac86d69f2`。
该 ID 来自临时 Worker 保存的工具结果，并非模型编造。

相关调用链：

- [worker.py](../investigation/worker.py) `_context()` 第 230 行起重算派生分析；
  第 358–367 行通过 `chain_fresh` 和 `restore_context()` 选择完整链；
  第 368–382 行追加带 `context_origin=runtime_derived_metric_analysis` 的 user 输入。
- 同文件第 798–800 行 `_run()` 保存 `protect(history + response.output)`，
  第 806 行起保存模型响应；下一轮因此会读到先前的 Runtime 分析。
- [checkpoint.py](../investigation/checkpoint.py) 第 119 行起的 `restore_context()`
  在可信、合法链条件下直接复用 history，没有对 Runtime 派生输入进行替换。
- `_context()` 不原地追加已存 history，且 Checkpoint 根字段没有 `metric_analysis`，
  这两件事都不能证明多轮不累积：实际持久化位置是 `history[].content` 内的 JSON。

该复现仅表明派生内容重复，不表明所有重复字段都应删除。
工具调用、真实输出、当前证据和派生历史分析仍有各自用途。

  每个场景总计最多 7 次 Mock 模型交互；没有调用付费模型。

  `json.dumps(ensure_ascii=False, allow_nan=False)` 的 UTF-8 长度，含默认分隔空格。
  完整请求额外包含 model、instructions 和 tools。二者均是统一测量序列化，
  **不是已测得的 SDK HTTP 线路字节**，不含认证头。
- token：已安装的 tiktoken 0.14.0，使用 `o200k_base` 对上述 JSON 文本进行
  `encode_ordinary()` 的精确计数。仅在临时缓存中读取校验通过的编码数据；
  编码文件来自 [公开静态资源](https://openaipublic.blob.core.windows.net/encodings/o200k_base.tiktoken)，
  SHA-256 与本机已安装包中的预期值一致：
  `446a9538cb6c348e3516120d7c08b09f57c36495e2acfffe59a5bf8b0cfb1a2d`。
  未安装新依赖，未改用户既有缓存。测试内禁止外部网络；缓存缺失时统计明确为空。
- **这些是参考编码器的 JSON 文本 token，不是 `deepseek-flash` 的原生输入 token，
  不包含其隐藏消息封装，不是计费值。** Mock Response 没有 usage，原生 token 统计均不可用；
  本地也没有可据此确认目标 Provider 上下文容量的配置。
- 分析份数同时统计重建消息中的非空字段和 Runtime 补充消息；补充消息另行计数。
  重复按完整 `metric_analysis` 值哈希判断，不把变化的采集外壳时间当作分析变化。
- CP 字节从 SQLite 的 Checkpoint data 原文读取；逐次验证模型校验、重新编码相等、
  重新只读打开 SQLite 后内容相等。保留数量始终不超过原配置 4 个。
  该数值不是 SQLite 文件含空闲页和索引的物理大小。
- 请求前 CP 在本轮模型额度预留后读取；响应后 CP 在模型响应提交后、该轮工具输出
  保存前读取。中间状态允许有 pending 调用；下一请求前及最终 history 校验所有完整调用对。
  超时轮使用失败落盘点，不把没有收到的响应标为成功。

## Checkpoint 上限实验与模型上下文风险

原单份分析值最多 32768 字节，但这不是整个 history 的总上限，字符串嵌套还会产生
JSON 转义开销。原总 Checkpoint 上限仍为 4,194,304 字节，未作调整。

本轮小载荷最终 CP 约占上限 0.57%，不能得出“默认 7 轮就会撞到 4 MiB”的结论。
为了区分余量风险，另用相同 7 轮的完整 Checkpoint 做纯存储实验：
在临时副本内加入每段小于 65536 字符的合成合法 user 前史，只用于控制容量余量；
与“保留最新一份分析”的诊断副本比较，不把大前史发给模型，也不修改生产消息链。

| 项目 | 实际结果 |
| --- | --- |
| 保留最新分析的诊断副本 | 4,188,279 字节，成功落盘并重开 |
| 保留 6 份分析的原行为副本 | 4,200,329 字节 |
| 5 份重复造成的差值 | 12,050 字节 |
| 原上限与拒绝 | 4,194,304 字节；checkpoint_size_limit |
| 失败后的持久化 | 事务回滚，Session checkpoint_id 和原已存内容保持一致 |

这证明已接近上限的合法前史可能因重复分析更早耗尽容量，不是自然生成 4 MiB
上下文的概率测量，也没有复现完整 Worker 在该错误后的所有故障处理分支。
模型上下文同样会因额外输入更早消耗，但没有真实 Provider 容量、原生分词器、
usage、隐藏封装或服务端截断信息，**不能确认本例是否已经接近或触发模型上下文限制**。

其他会影响风险的变量包括：每轮实际耗时与证据 TTL、Provider 是否启用完整链、
分析有效载荷及降级、工具 schema 大小、其他工具输出和模型 reasoning 大小、
实例身份变化、人工消息造成的重建、重试对 history 的清空以及 Checkpoint 保留数量。

## 最小修改建议（未实施）

建议单独安排一个局部修复：只在 `_context()` 的 complete_chain 分支构建新输入时，
识别 Runtime 自己追加的派生分析输入，更新为最新一份，避免继续携带相同旧副本。
保留其他消息顺序、所有真实 function_call/function_call_output 及其参数、输出和 ID，
保留 provider_verified、valid_chain、chain_fresh、重建分支、记录和预算原规则。

不应按所有 user 消息删除，也不应通过一律强制重建来绕开问题。按来源 ID 去重还不足以
判断分析是否更新：证据内容、选择统计、配置或分析实现也可能变化，采集外壳时间本身
