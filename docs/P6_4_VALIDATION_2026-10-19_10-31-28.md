## 2. 当前实际调用链与三个判断层

当前调用链为：

`Worker.run_once → Manager.recover → RuntimeStore.claim → Agent.request_durable_response → ModelClient.call_once → 脚本化 SDK responses.create → Worker 保存 response_saved → ToolManager.run_tool → 已注册 Tool / Provider → tool_saved → 下一模型轮 → Agent.handle_final_answer → Worker._finish → RuntimeStore.checkpoint → Manager.sync_incident → workflow / Web 结果投影`。

ModelClient 继续使用 SDK `max_retries=0`，重试、累计预算和持久化仍由现有 Runtime 管理。

| 判断层 | 实际含义 | 本轮处理 |
|---|---|---|
| 流程 | Session 的 RUNNING / COMPLETED / FAILED 等；答案的 success/status | 保留既有含义和状态机。非空最终回答可以完成流程，内容仍可能错误。 |
| 机械验证 | 数据结构、引用身份、原件来源与哈希等确定性检查 | 生产出口明确 `result_schema_only`；案例 A 另复用 P5/P6.3 验证引用和冻结原件，标注 `frozen_references_and_hashes`。 |
| 语义审查 | pending_review / rejected / accepted | 未审查保持 pending_review；Agent 拒绝意见可阻止可信提升。本轮无 accepted 操作和真人审批入口。 |

`Agent.handle_final_answer()` 原先直接包装 `success=True/status=completed`；Worker 将原答写入 Checkpoint 并将 Session 转成 COMPLETED；Store 校验及冻结统计并不验证自然语言事实。原先 `workflow()`、Web Session 答案、Incident 历史答案均未提供独立语义状态。

本轮只读投影新增 `ResultTrust`：机械状态及范围、semantic_status、trusted、human_approval、原答 UTF-8 SHA、拒绝理由和审查来源。生产出口不读取模型或旧记录自报的可信标签。所有生成路径仅能产生 pending_review / rejected，`trusted=false`、`human_approval=not_recorded`；accepted 仅为预留枚举值，不能通过调用投影函数获得。

Session 答案沿用 `InvestigationResult` 校验；Incident 历史沿用没有 success 字段的 `InvestigationRecord`，通过明确的 history_record 参数选择，未改持久化格式。Web 哈希绑定的是脱敏、8000 字符截断前的完整保存答案，不是展示片段。

本轮明确保持：`Session COMPLETED ≠ Semantic ACCEPTED`，`Reference Exists ≠ Claim Supported`，`HTTP 200 / Health OK ≠ Business Recovered`。

## 3. 案例 A：P6.3 原始失败回答

入口：[p64_historical_acceptance.py](../scripts/p64_historical_acceptance.py)。本地结果为 `data/p64-historical-acceptance-20261018-01/acceptance.json` 和独立 `sha256.json`。

结构结果仍为 passed，原 P5 strict_acceptance 仍为 pending；新的独立投影为 **rejected**，没有回写或改写任何原件。

**事实和意见分开**：文件一致性、五个响应及时间比较为本轮机械复算；五项自然语言支持程度仍有明确 Agent 审查来源；真人最终决定未取得。哈希只验证本地一致性，不能认证外部现实或独立来源真实性。

## 5. Checkpoint、恢复、预算和权限

- 本轮真实持久化边界观察到 `model_started`、`response_saved`、`tool_started`、`tool_saved`。`investigation_completed` 是审计事件及 Session 转换，**不是额外的 Checkpoint.phase**；最终 phase 仍可为 response_saved。
- 恢复场景在 tool_checkpoint_committed 后抛测试专用 BaseException，保证工具原件已提交、function_call_output 尚未提交；先读回中断状态，再仅推进隔离 Store 注入时钟到原 lease+1 秒。
- 随后重新走 Manager.recover / RuntimeStore.claim（由 Worker.run_once 调用）；本次实际 fencing 从 1 到 3，旧 owner/fence 被 Store.guard 拒绝。指标记录仅一条，未完成调用被 abandon，没有补造成功输出。
- 推进时钟后旧指标保持原 collected_at/evaluated_at，进入 expired=true / use_for_current_state=false 的历史观测；不能重新变成当前健康证据。
- 复用现有 Runtime 的六种真实子进程退出边界测试（model/tool 的 before_io、after_io、checkpoint_committed）、已保存 final 恢复、稳定 SHA 源码缓存、动态指标过期重查、事务/CAS/lease/fencing 测试。本轮没有新建第二套恢复状态机。
- 单次尝试仍为 MAX_AGENT_LOOPS=7 / MAX_TOOL_CALLS=13；生命周期预算沿用原 RuntimeLimits。P6.1 和 Runtime 既有预算测试验证第 14 次工具不能执行、第 8 轮不能突破尝试限制，以及 resume / cache / 失败调用的计数边界。本轮没有调整配置或生产预算。
- 非法工具、跨服务和修复请求在 Worker 原校验边界被拒绝。普通人类消息和调查结果均不构成 Remediation 正式授权；本轮没有修改审批或执行代码。
- Mock 作用域封禁 socket connect/connect_ex/create_connection/getaddrinfo/sendto、真实 OpenAI 构造、外部 PostgreSQL 的 psycopg 连接、子进程和线程启动；真实临时 SQLite 连接用于验证持久化，Provider HTTP 只由离线夹具响应。另有负测：Mock 工具尝试 loopback 连接也在实际连接前被 BaseException 拒绝。
